## How these boundaries were drawn, and why not by directory

Story 4.3's `## Spec Change Log` records that a phase split drawn **by directory** ("leave all of
`src/**` untouched") left the tree red between phases: three `message_keys!` entries landed with no
`vi.json` counterpart and `tests/ipc_contract.rs` sat at 27/29, so the next phase would have
measured its own new tests against an already-red suite. Story 4.4's phase file drew its
boundaries by task for that reason. This file does the same, and three pairings are load-bearing.

- 🔴 **Task 3 (`core/i18n/mod.rs`) and the six cause sentences of Task 5 (`src/i18n/vi.json`) are
  one phase.** A `MessageKey` with no `vi.json` string fails
  `ipc_contract.rs::every_message_key_exists_in_vi_json` (`:232`), and a placeholder mismatch fails
  `:325` in both directions. This is the exact pairing 4.3 split.
- 🔴 **Task 5 splits by CONSUMER, not by file.** Its six cause sentences belong to Phase 1 with the
  keys that require them. Its `command.<id>` label keys belong to Phase 2 with the registration
  that requires them — `check-commands.mjs:994` wants a `command.<id>` label for a registered id,
  so a label added a phase early is an orphan and a registration added a phase early is red.
- 🔴 **Task 9 splits across Phase 1 and Phase 3, and neither half is optional.** Remapping the
  seven variants onto six keys makes the EXISTING cases red —
  `ai_translate_contract.rs:964` pins all seven to one key with its documented `retryable` flag,
  `:941` pins the non-2xx key, `:953` the stream-ended key, `:1733` the batch pair. Repairing those
  four is **Phase 1's** work, because a phase may not hand the next one a red suite. The NEW
  coverage the task also asks for — a failure with zero tokens received on both paths,
  `work.none_open` on the batch path, `:1733` widened to every variant, and the counter-check by
  removal — is **Phase 3's**.
