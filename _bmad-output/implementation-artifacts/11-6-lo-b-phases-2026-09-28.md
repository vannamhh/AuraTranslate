### Progress/cancel architecture (L9276/L9889) — read this before touching it further

To avoid an ~80-call-site ripple across `tests/**` (`create_work`/`append_chapters_to_work` alone have 70+6 direct test callers), every layer in the `create_work` → `prepare_chapter_images` chain got a **parallel `_with_progress` function that does the real work**, while the **original name/signature becomes a thin wrapper that forwards with silent no-op closures** (`&mut |_, _| {}`, `&|| false`). This preserves 100% of existing test call sites unchanged. The chain, real name → wrapper:
`prepare_chapter_images` (signature changed directly, private, 2 call sites) ← `create_work_with_progress`/`create_work`, `append_chapters_to_work_with_progress`/`append_chapters_to_work` (`work_creation.rs`) ← `confirm_import_with_encoding_with_progress`/`confirm_import_with_encoding`, `confirm_append_import_with_encoding_with_progress`/`confirm_append_import_with_encoding`, `confirm_append_import_with_encoding_indexed_with_progress`/`confirm_append_import_with_encoding_indexed` (`mod.rs`). Only `wire::confirm_import_with_encoding`'s three branches call the `_with_progress` names with real closures (`app.emit` + `ImageDownloadGeneration`); every `tests/**` caller and every other wire command still calls the plain names. Same trick for the page phase: `fetch_url_import_items_with_progress`/`fetch_url_import_items` in `url_import.rs`.

If a later change needs progress/cancel on another entry point (e.g. `create_work_from_file`'s docx path), thread it the same way — don't add a third parallel set of names.

### The APPEND/`replace_open_work` race — investigated, not fixed (per this phase's own scope)

Asked to settle: can an in-flight APPEND into Work X (asset files written, `asset` rows not yet committed) race `replace_open_work` opening X, whose orphan sweep would then delete those files? **Yes, structurally possible, in one specific branch — not the one the existing code comment already reasons about.**

- `wire.rs:894-924` (`confirm_import_with_encoding`'s "already open" branch — APPEND into the *currently open editor Work*) is **not** racy: the `OpenWorkState` `MutexGuard` taken at `:896` is held for the *entire* `confirm_append_import_with_encoding_with_progress` call — image download, `fs::write`, and the final `store.write` transaction all happen before the guard drops at the end of that `if` block. Any concurrent `replace_open_work` targeting the same Work blocks on the same mutex until this command is fully done (files written *and* rows committed), so its sweep only ever sees consistent state. This is the branch the `🔴 SỬA 2026-09-16` comment at `wire.rs:897` already reasons about, for a different concern (the check-then-relock window), not this one.
- `wire.rs:925-968` (the "not already open" branch — APPEND into a Work that is *not* the currently open editor Work) **is** racy. `open_destination_for_append` (`mod.rs:3187`) → `open_work` → `Store::open` opens a **fresh, independent** connection, entirely outside `OpenWorkState` — confirmed by the doc-comment at `wire.rs:940-947` itself ("nhánh này không giữ bất kỳ khoá `OpenWorkState` nào"). Inside `confirm_append_import_with_encoding_indexed`, `prepare_chapter_images` writes every image file to disk in a loop (`work_creation.rs:1171`+) **before** the single batch `store.write` transaction that inserts all `asset` rows for this call (`work_creation.rs:846`) — same "files before rows" ordering as `create_work`, and the same accepted trade-off named in that function's own doc-comment. If a **second**, concurrent command also touches Work X during that window — most plausibly another `open_work(X)` or another APPEND into X finishing first and calling `replace_open_work(app, X)` — its sweep runs `SELECT file_name FROM asset` against X's `project.db` and deletes any file in `X/assets/` not yet named by a committed row, including the first command's in-flight images. Nothing in `open_destination_for_append`/`Store::open` serializes two independent opens of the same `project.db` against each other; `#[tauri::command(async)]` means two webview-issued `invoke()` calls genuinely can run concurrently on Tauri's async runtime.
- Not fixed: no seam here is a guard (nothing asserts this ordering today, so there is nothing to counter-check), and a real fix needs a decision (a per-Work-id lock registry? extend `OpenWorkState` semantics? serialize `open_destination_for_append` some other way?) that's an architecture call, not a one-line patch. Recording it plainly per instruction, for the Ledger phase to turn into an owned debt item (`Chủ: Epic 11` or `Chủ: Ice` — a real-use pass alone won't reproduce this; it needs either a new regression test that drives two concurrent commands, or a design decision first).
