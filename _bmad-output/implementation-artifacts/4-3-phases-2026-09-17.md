  🔵 **CORRECTION 2026-09-17 (post-handoff, before Phase 3 started)** — the ORIGINAL version of
  this phase shipped `key_configured: bool` and made the whole `ai_config_get` call fail

  names ("A value that can be UNKNOWN gets an `Option`/`NULL`, never a `0`") — `false` would make

  same tone as a retryable error elsewhere in the section), and the row's save/delete actions

🔴 **The mock must be installed before the FIRST keychain touch in the binary, not before the
first `set`.** Phase 2 measured this the hard way: with a real entry present, a freshly compiled
binary reading it back raised a macOS authorization dialog and the run hung — a hang, not a red
case, so nothing reports it. Two facts make this sharper than Phase 2's note says:

- `commands/aiconfig.rs:182` probes the keychain on every `ai_config_get`, so the touch that
  trips the dialog is a **read**, and it happens in cases that have nothing to do with the key.
  `aiconfig_contract.rs`'s ten pre-existing Story 4.2 cases already call that path.
- Therefore the hazard is not confined to cases this phase writes. If the developer running the
  suite has ever saved a real key through the app, today's `aiconfig_contract` can hang on
  their machine with no code change at all. Installing the mock once, before any test in the
  binary runs, is what removes that — and the guard the spec asks for (`Entry::store_status()`
  is `Ok`, fail loudly otherwise) is what stops a missed install from looking green.

If a one-time init before all tests in a binary has no existing precedent in this repo, say so
and describe what you used instead rather than inventing a pattern silently.
