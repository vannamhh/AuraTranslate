## 🔴 How these boundaries were drawn, and why not by directory

Story 4.3's `## Spec Change Log` records that its phase split **left the tree red between
phases**: Phase 1's boundary was drawn by directory (*"leave all of `src/**` untouched"*) while
one task bundled `core/i18n/mod.rs` with `src/i18n/vi.json`. Phase 1 added three `message_keys!`
entries with no `vi.json` counterpart and stopped, leaving `tests/ipc_contract.rs` at 27/29. The
next phase would have measured its own new tests against an already-red suite.

So these boundaries are drawn **by task, never by directory**. Two pairings are load-bearing and
must not be separated:

- **Task 3 (the migration step) and Task 4 (the version-number ripple) are one phase.** Adding a
  `Migration` entry without re-measuring the hard-coded version numbers in
  `pinned/store/project/glossary/segment_contract.rs` leaves the Rust suite red. Task 4's own
  rationale records the measured size of that ripple — 6–10 files, 27–99 numeric lines; do not
  plan against the understated figure in spec 4.3.
- **Task 8's two halves — `core/i18n/mod.rs` and `src/i18n/vi.json` — are one phase.** This is
  the exact pairing 4.3 split. A `MessageKey` with no `vi.json` string fails
  `ipc_contract.rs::every_message_key_exists_in_vi_json`.

**Every phase ends on a green tree.** Before writing your notes back, run `npm run build` then
`cd src-tauri && cargo test --locked`, and from Phase 4 on also `npx vitest run`. Record the
counts you measured, not counts you carried forward from this file.

### 🔴 Fix this defect first — found by the orchestrator in Phase 1's diff, measured, not inferred

`core::promptset::vars::scan_markers` mis-reports a body that contains a stray `{{` **before** a
real marker. The scan takes the NEAREST `}}` after each `{{`, so the stray opener swallows the
marker that follows it. Measured against the real product code (temporary integration test, since
removed — the tree is clean):

```
CONTROL  "{{glossary_terms}}"                    -> glossary_terms_missing = false   (scan works)
ACTUAL   "ghi chu {{ rieng: {{glossary_terms}}"  -> glossary_terms_missing = true    (WRONG)
                                    unknown_markers = ["{{ rieng: {{glossary_terms}}"]
```

Two warnings are wrong at once: it names a "token" the user never wrote, and it claims Glossary
Enforcement is off for a body that **does** carry `{{glossary_terms}}`. That breaks the spec's AC
*"a warning names that token"* and the I/O Matrix row for a missing `{{glossary_terms}}`.

This is not an exotic input — Decision 3 exists precisely to allow `{{` as ordinary text, so this
is the case that decision creates. The eight unit tests in `vars.rs` do not reach it:
`an_unclosed_double_brace_does_not_panic_or_reject` uses a body with no later `}}` at all, so it
hits the `break` instead.

Fix in `vars.rs` and add cases for it. A workable rule: when the text between `{{` and the nearest
`}}` contains another `{{`, restart the scan from that inner `{{` rather than consuming the whole
span. Keep Decision 3 intact — still never reject, still never panic, and an unmatched `{{` with
nothing after it must stay silent. Add a case for the CONTROL line above too, so the next change
cannot break detection without a red.
