**Disposition 2 — `spawn_import_scan` unification (L8989 + L9226 + L11142)** — measured first (see Measurements), stayed within budget, landed.
- `spawn_import_scan(app, work_id, chapter_id: i64, source_lang)` → `spawn_import_scan(app, work_id, chapter_ids: Vec<i64>, source_lang)` (`commands/project/mod.rs`). **One `ImportScanGeneration::next()` call for the whole batch, not one per Chapter** — `ImportScanGeneration` is a single app-wide `AtomicU64`; calling `.next()` N times (the naive "call the old single-chapter function N times" shape) would have self-cancelled (N−1) of a batch's own scans, reproducing L8989's bug in a new form. One spawned `std::thread` loops `chapter_ids` sequentially, checking `current()` at the top of each iteration (a Work closing/changing mid-batch stops the *remaining* Chapters silently, same I/O-Matrix rule as before, now per-iteration instead of per-call).
- `config`/`disabled`/`layers`/`lang` (read from `GlobalConfig`/`DictLayers`) are loaded **once per batch**, hoisted out of the per-Chapter body — the old code reloaded `app_config` from `global.db` on every call, which would have meant N redundant reads at N=2000. The per-Chapter body (two short `OpenWorkState` locks, scan, enqueue, write, emit — unchanged mechanism) is now `run_one_chapter_import_scan`, called once per id in the loop, so the "hold the lock for at most one Chapter" invariant is unchanged even though N Chapters now get scanned per spawn.
- New `OpenWork::new_chapter_ids: Vec<i64>` — the chapter ids written by *this* `create_work`/`append_chapters_to_work` call ("of THIS call" semantics, same convention as `images_saved`/`source_lang_mismatch`). `create_work`'s write closure now returns `(first_chapter_id, Vec<i64>)` instead of just the first id; `append_chapters_to_work` sets `open.new_chapter_ids` directly (same pattern it already used for `images_saved`/`images_failed`/`source_lang_mismatch`). `open_work` sets it to `Vec::new()` (reopening writes no new Chapters). This field does **not** cross IPC (`CreatedWork` unchanged) — `spawn_import_scan` is Rust-internal, the wire only reads `opened.new_chapter_ids`/`open.new_chapter_ids` before `replace_open_work` moves the value, same "chốt trước khi move" pattern the file already used for `chapter_id`.
- Wired from all three call sites in `wire.rs`: `create_work_from_text`/`create_work_from_file` (N always 1, no shape change), `confirm_import_with_encoding`'s new-Work branch (pattern-split and URL-list, real N), and — **new** — the APPEND branch, which previously spawned no scan at all (the old comment explicitly declined this as undone debt; Disposition 2 closes it). The APPEND branch now captures `new_chapter_ids` from `open`/`opened` in both its `already_open` and indexed-reopen sub-branches before the value moves, and spawns at the very end using the same `keep_committed_import_when_scan_spawn_fails` pattern as the other two paths.

### What was wrong

`core/segment/encoding.rs::render_candidates` only ever decoded [`EVIDENCE_WINDOW_BYTES`] (4 KiB) of raw bytes per candidate, normalized that raw window, and handed the result out as both the top-level `EncodingCandidateWire.normalized` field AND (via `pipeline_window`) as the `display_window`/`window_truncated` fed into `commands::project::encoding_candidate_wire → cleanup_and_chapters_preview_for`. On the URL path (`PipelineShape::Chapters`, `extract_main_content = true`), that raw window still carries page chrome (nav/footer) that the real pipeline's `Step::ExtractMainContent` strips before writing — so the preview's displayed text, its span offsets, and its join/blank-line counts were all computed against a different text than what confirm actually writes. `cleanup_and_chapters_preview_for`'s own `chapters`/`blocks` fields were already extraction-correct (Story 6.10a passes the *original* N-chapter shape through the real `run_pipeline`, per-candidate) — only the Tier-1 `normalized`/`pipeline_window` pair (chapter-0-only, computed inside `encoding.rs` itself, never touching `run_pipeline`) was stale.

### Landed

- `render_candidates(bytes, source_lang)` → `render_candidates(bytes, source_lang, extract_main_content: bool, url_label: &str)` (`core/segment/encoding.rs`). `false` (every non-URL path — `Blob`, `Files`, bilingual) is byte-for-byte the old code path, unchanged. `true` (the URL/`Chapters` representative unit only — Tier-1 preview was never N-chapter-spanning, it only ever describes `chapters.first()`, same as before) routes through a new private `extracted_normalized_and_window`: decode the **whole** `bytes` under the candidate's encoding with `Encoding::decode_without_bom_handling_and_without_replacement` (the same strict, no-replacement decode `core::segment::pipeline::decode_unit` uses at confirm — not `decode_prefix_streaming`, which is deliberately lenient about a dangling multi-byte sequence at a *window* boundary, a leniency that doesn't apply to a whole-document decode), strip a leading BOM, call `crate::core::webimport::extract` + the pipeline's own `pub fn effective_kept_for_blocks`/`join_kept_blocks` (no overrides — same "nobody has touched Tier 2 yet" default the real pipeline uses when `block_overrides` is empty), then normalize the **extracted** text.
- Normalizing the extracted text reuses the self-declared branch's mechanism, not the window-decode branch's: `normalized_self_declared`'s body was factored out into a private `normalized_from_full_text(text, source_lang)` (both callers have a whole real string in memory now, not a pre-truncated window, so both just compare `text.len()` against `EVIDENCE_WINDOW_BYTES` and let `normalize::normalize_window` decide truncation) and the existing `pub fn pipeline_window_for_self_declared` is reused as-is for the safe display window. `EVIDENCE_WINDOW_BYTES`/`normalized_candidate`/`pipeline_window_for` (the `false`-branch functions) are untouched — Decision 11's "4 KiB window stays" is about `detect()`'s confidence voting, which this phase never touched.
